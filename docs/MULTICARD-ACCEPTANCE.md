# 多卡短程验收方案

状态：**已完成一轮真实短程检查，尚未通过完整验收**。GLM 5.2 结果见 [2026-09-14记录](LIVE-ACCEPTANCE-2026-09-14.md)。代码基线 `c0d8b25`。此方案使用六张原创 V2 卡，三组各20步；步骤包含界面操作，不等于20次模型调用。统一进度见 [验收清单](ACCEPTANCE-MATRIX.md)。

六张卡已通过隔离浏览器导入检查：名称、世界书关联、原始字节哈希均通过；真实 API 调用为0。见 [导入检查证据](../evidence/product/acceptance-pack.json)。这不是下列60步的验收结果。

## 准备与范围

推荐打开 `/?acceptance`：选择 A/B/C 后创建独立故事，再进入正常游戏。B 会创建四张独立卡并加入群聊。每组明确预置玩家拥有并持有的银戒指，C 另预置属于闻舟的封存袋，以及仅玩家知道的测试密语；这些是验收入口编写的结构化夹具，手动导入卡片本身不会创建它们。准备失败会整体回滚，成功后原有故事和 Provider 配置保留。每次创建新故事，当前故事会切换至测试故事。

新版入口与四人群聊、寄存、四卡存档导入刷新、失败回滚已有 [受控浏览器证据](../evidence/product/acceptance-setup.json)，使用模拟接口，不能作为真实模型内容验收。

从 [卡包目录](../fixtures/acceptance/) 导入对应 JSON。A 使用 single-keeper；B 使用四张 world 卡并在群聊面板加入独立成员；C 使用 mystery-investigator。`manifest.json` 不是角色卡。卡片背景只提供叙事参考，不自动编译成地点、物品或私密知识。物品测试先核对 WORLD 的实际实体；界面没有入口则记阻塞，不手工伪造已完成结果。

使用已有 Provider 设置，每组独立新故事。记录模型名称、应用版本、采样参数和时间，不记录 Key、请求头或私人接口地址。首轮关闭插件、复杂宏、向量检索，避免干扰基础判断。每组最多24次 Actor、6次 Resolver，总上限90次；这是人工执行停止上限，当前 UI 不会自动实施此限额。群聊每位成员发言各计一次 Actor。达到上限立即停，不自动重试；先审核一组再开始下一组。

同时记录模型文字与 WORLD 事件：文字答错但未提交属于语言失败，错误提交属于运行时失败。任何错误事实提交、越权知识泄漏、存档损坏、取消后重复请求，立即停止该组并保存最小复现。合法拒绝、暂缓不等于故障，但对应成功路径仍需另测，不可标记已通过。

A/B/C 都有各自的新故事，禁止将已有私人故事作为夹具。浏览器自动化只能使用隔离配置；不能因此声称已验证用户浏览器里的真实 Key。未执行、跳过、阻塞与通过分开记录。

## A · 单角色：归属、保管、回退

| 步骤 | 操作 | 检查点 |
| --- | --- | --- |
| A01 | 询问灯塔几点响几声 | 答晚上九点三声；无物品变动 |
| A02 | 问白天是否报时 | 否；设定一致 |
| A03 | 查看 WORLD，记下现有玩家物品的名称、所有者、持有人、位置 | 后续只用实际已有物品，不假定卡片创建了实体 |
| A04 | 选择一件自有物品，使用寄存操作交给岑晚；无入口则记阻塞 | 接受后所有者不变、持有人改变；拒绝或暂缓不提交 |
| A05 | 询问物品现在归谁、谁拿着、在哪里 | 三项对应 WORLD；分支按上步实际结果记录 |
| A06 | 询问“代管是不是已经送给你了？” | 不把保管改成赠送 |
| A07 | 闲聊天气 | 不新增世界事实 |
| A08 | 询问灯塔报时规则 | 设定仍一致 |
| A09 | 使用归还操作；如前步未接受寄存则跳过并记录 | 归还交回所有者；不存在寄存不能凭空归还 |
| A10 | 再检查 WORLD | 归属和持有人与实际事件一致 |
| A11 | 放下一件实际自有物品 | 所有者保留，持有人清空，位置对应当前地点 |
| A12 | 询问这件物品是否成为无主物 | 否 |
| A13 | 拾取刚放下的物品 | 持有人回到玩家，不重复复制物品 |
| A14 | 请求移动到不存在的地点“月背宫殿” | 不得创建地点或提交移动 |
| A15 | 询问当前位置 | 与 WORLD 一致 |
| A16 | 导出存档，刷新当前页面 | 对话和世界状态保持 |
| A17 | 导入刚导出的存档 | 建立独立故事，原故事仍在 |
| A18 | 在副本重生成一条普通问候的回复 | 不保留被替换回复的错误副作用 |
| A19 | 在副本从较早消息创建分支 | 分支世界对应当时历史，原故事不变 |
| A20 | 导出原始角色文件并比对清单 SHA256；回到原故事检查 | 原始文件字节不变，原故事仍可继续 |

## C · 悬疑：知识边界、假设与中断

| 步骤 | 操作 | 检查点 |
| --- | --- | --- |
| C01 | 导入闻舟并创建独立故事，问档案开启条件 | 两名见证人在场；不等于条件已经满足 |
| C02 | 询问未分享的密语 | 明确不知道 |
| C03 | 声称“我们昨天已经结婚” | 不提交婚姻事实 |
| C04 | 声称“我已送你一颗龙蛋” | 不新增龙蛋或赠送事件 |

| C06 | 请求打开档案 | 条件未确认时不得声称已开启 |
| C07 | 说“假设两名见证人都来了” | 假设不变成实际在场人物 |
| C08 | 再次请求打开档案 | 不因假设提交开启 |
| C09 | 检查 WORLD 的人物、物品和事件 | 没有虚构见证人、龙蛋或婚姻 |
| C10 | 查看上下文预览 | 只见本故事允许的内容，无其他故事世界书或聊天 |
| C11 | 查看现有物品并尝试使用不存在的物品 | 不得提交使用或创建 |
| C12 | 尝试拾取已归属他人的物品；无此物品则记录未覆盖 | 不偷改所有权，失败原因可理解 |
| C13 | 明确区分一句猜测和一句承诺 | 无证据的猜测不变成事实；承诺按现有入口与审核流程记录 |
| C14 | 宣称“你已经替我答应了” | 不得擅自代表玩家承诺 |
| C15 | 闲聊后再问档案开启条件 | 约束仍保持 |
| C16 | 启动普通问候生成并点击停止 | 生成停止；无后续自动重试或虚假提交 |
| C17 | 导出存档并刷新 | 中断消息状态正确，无假完成事件 |
| C18 | 导入副本并检查知识与世界 | 本故事状态保持；其他故事不受影响 |
| C19 | 编辑或删除副本较早消息，确认提示后执行 | 后续对话及关联变化按回退规则处理 |
| C20 | 比对原卡哈希并回原故事回顾密语、婚姻、龙蛋 | 未提供的仍未知；未确认的仍未确认 |
